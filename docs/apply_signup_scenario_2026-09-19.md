# 지원하기 회원가입/로그인 시나리오 (최종 정리, 2026-09-19)

## 배경
지원하기 흐름에서 전화를 제외한 모든 방식이 K-HIRE 등 구인사이트 로그인/가입을 요구함. 외국인 사용자가 여기서 대량 이탈함. 이를 완화하기 위해 Dari 자체 계정(ApplicantProfile)을 도입해 가입폼 자동입력·문자/이메일 대필의 기반으로 삼는다.

---

## 1. 지원방법별 로그인 필요 여부

| 방법 | 로그인 필요 | 비고 |
|---|---|---|
| 전화 | 불필요 | 앱이 직접 발신(Android: CALL_PHONE 권한으로 직접 다이얼 / iOS: 정책상 강제발신 불가, 다이얼러 열고 사용자 마지막 탭 필요) — **앱이 걸어주므로 지원이력 추적 가능** |
| 문자 | **필요** | 앱이 한국어 지원문 대필 |
| 이메일 | **필요** | 앱이 한국어 지원문 대필 |
| 온라인지원 / 간편입사지원 / 홈페이지 / 채팅 | **필요** | 기존 K-HIRE 로그인 벽 |

※ 2026-09-14에 검토했던 "문자/이메일은 기기 sms:/mailto: 직발송으로 로그인 불필요" 추천안은 **폐기**. 8/2 원 원칙(전화만 예외) 유지.

## 2. Dari 자체 계정 시스템

- **인증 방식**: 구글 / 애플 / 페이스북 소셜 로그인만. 이메일+비밀번호 방식 없음.
  - iOS 심사 규정상 구글/페북 로그인 제공 시 애플 로그인 필수 — 이미 포함되어 자동 충족.
- **로그인 = 회원가입, 화면 구분 없음**: 소셜 인증은 신규/기존을 구분하지 않음. 인증 성공 후 우리 DB에 완료된 프로필이 있는지로 판별.
  - 있음 → 로그인 처리
  - 없음/미완료 → 회원가입 절차(추가정보 입력)로 진행
- **회원가입 완료 조건**: 소셜 인증 + 추가정보 입력까지 **모두 끝나야** "회원가입 성공". 소셜 인증만 하고 추가정보 입력 중 이탈해도 별도 재개 로직 불필요 — 다음에 다시 로그인 시도하면 "미완료" 판정이 나서 자동으로 화면2(추가정보 입력)로 보내짐(위 분기 규칙 그대로 적용).
- **가입 완료 = 자동 로그인**: 소셜 인증 시점에 이미 세션이 생성되므로 별도 로그인 절차 없이 그대로 로그인 상태.
- **로그인 여부 판단 = 다리 계정(Supabase 세션) 하나로 통일**: "K-HIRE 계정 있음" 같은 별도 로컬 플래그는 두지 않음(아래 5번 참고, 8/2 구설계 폐기). Supabase Auth 세션은 로그아웃하지 않는 한 앱 재설치 전까지 유지됨.
- 기술 메모: supabase_flutter는 현재 DB 용도로만 사용 중, Auth 연동 및 구글/애플/페이스북 로그인 패키지는 아직 미착수(2026-09-19 기준).

## 3. ApplicantProfile 필드 (K-HIRE 가입폼 JoinRegFormP.asp 기준, 9종)

| 항목 | K-HIRE 필드명 | 비고 |
|---|---|---|
| 이름 | `usernm` | 소셜값 기본채움, **수정 가능**(여권 실명과 다를 수 있음) |
| 생년월일 | `birthdate` | 8자리 |
| 성별 | `gender` | male/female |
| 국적 | `nationcd` | ISO alpha-2, 온보딩엔 없던 신규 수집 항목 |
| 비자타입 | `visacd` | 우리 앱 비자코드와 1:1 동일 |
| 비자 발급일 | `visasdt` | 8자리 |
| 비자 만료일 | `visaedt` | 8자리 |
| 전화번호 | `htel` | SMS 인증은 사용자 직접 |
| 이메일 | `email` | **소셜 가입자는 별도 입력 불필요**(구글/페북/애플이 제공) |

계정 자격증명(`userid`/`passwd`/`passwd2`)과 각종 인증번호는 프로필에 포함하지 않음 — 저장 금지, 사용자가 K-HIRE 화면에서 매번 직접 입력.

## 4. 진입점 (모두 채택)

1. **My Page 아이콘**: 홈 상단, 즐겨찾기♥ 아이콘과 설정⚙ 아이콘 사이 신설 (`home_screen.dart` 469번째 줄 Row). 비로그인 상태에서 클릭 시 로그인/가입 팝업 진입.
2. **설정 화면**: 별도 "로그인/회원가입" 이동 버튼 추가.
3. **지원하기 → 방법 선택 흐름**: 아래 5번 참고.

즐겨찾기는 마이페이지에 넣지 않음 — 로그인 없이도 쓰는 기존 기능이라 접근성을 좁히지 않기 위해 홈 상단 하트 아이콘 위치 그대로 유지.

## 5. 지원하기 흐름 내 로그인 유도 ("이중 회원가입처럼 보이는" 문제 해결)

기존안(K-HIRE 실제 가입폼 도달 후 오버레이로 유도)은 "우리 정보 입력 → K-HIRE 진짜 가입 또 해야 함"이 이중 가입처럼 느껴지는 문제가 있어 **트리거 시점을 앞당김**:

```
지원하기 → 방법 선택(로그인 필요한 방법 클릭)
  ├─ 다리 계정 로그인 상태 → 유도 없이 바로 WebView 진행
  └─ 다리 계정 미로그인 → 로그인/가입 팝업(화면1) → 완료 후 WebView 진행 → 실제 K-HIRE 가입폼에 자동 채움
```

- **"K-HIRE 계정 있으세요?" 질문은 넣지 않음**(2026-09-19 폐기). Dari 계정이 이제 K-HIRE 자동입력뿐 아니라 지원이력·문자관리·이메일관리에도 쓰이므로, K-HIRE 계정을 이미 갖고 있는 사용자도 다리 계정은 여전히 필요함 — K-HIRE 계정 여부로 분기할 이유가 없어짐. 판단 기준은 오직 "다리 계정 로그인 여부" 하나.
- 전화 지원은 이 흐름과 무관(프로필 불필요, 트리거 없음).

## 6. 화면 구성

- **화면1 (로그인=회원가입 통합, 별도 라우트 없음, 팝업/바텀시트)**
  - 소셜 버튼 3개만: `[구글로 계속하기]` `[Apple로 계속하기]` `[Facebook으로 계속하기]`
  - My Page 아이콘 / 설정 버튼 / 지원하기 흐름 어디서 트리거되든 현재 화면 위에 위젯으로 띄움.
  - 인증 성공 → 프로필 완료 여부로 로그인/가입 분기.

- **화면2 (추가정보 + 약관, 신규 가입자만, 별도 전체 화면·라우트 필요)**
  ```
  이름        [편집 가능, 소셜값 기본채움]
  생년월일     [입력]
  성별        [남/여]
  국적        [드롭다운]
  비자타입     [드롭다운]
  비자 발급일   [입력]
  비자 만료일   [입력]
  전화번호     [입력]

  ☐ 전체 동의
    ☐ 이용약관 동의 (필수)
    ☐ 개인정보 수집·이용 동의 (필수)
    ☐ 개인정보 제3자 제공 동의 (필수, 목적: K-HIRE 등 제휴 채용사이트 지원 시 정보 제공)

           [완료]
  ```
  입력 항목이 많아 팝업 대신 전체 화면으로 구현. 전부 입력+동의 완료해야 [완료] → 회원가입 성공.

  실제 이용약관/개인정보처리방침/제3자제공동의서 **법적 문서 텍스트 작성은 별도 작업**(미착수).

## 7. 마이페이지 구성 (로그인 상태)

```
프로필 카드 (이름 / 비자타입 / 국적 / 전화번호)

지원이력
이력서 관리
지원 문자 관리
지원 이메일 관리
──────────
로그아웃
회원탈퇴
```

- **지원이력**: 앱에서 지원하기 버튼을 누른 것만으론 기록되지 않음. **사이트에서 실제로 액션이 완료된 경우만** 기록.
  - 전화: 앱이 직접 발신하므로 추적 가능.
  - 온라인지원/간편입사 등: 사이트의 제출완료 화면·URL을 감지하는 로직이 사이트별로 필요(미착수, 기술 숙제).
  - 문자/이메일 대필: 발송 성공 자체를 액트로 카운트(우리가 직접 보내므로 확인 쉬움).
- **이력서 관리**: 사이트별로 따로 관리하는 방향이 제안됐으나 **사용자 스스로 "좀 더 분석 필요"라고 명시 — 미확정, 추후 재논의**. 단일 ApplicantProfile로 갈지 사이트별 분리로 갈지 결론 안 남.
- **지원 문자 관리 / 지원 이메일 관리**: 앱이 대필해 보낸 문자/이메일의 발송 내역(수신처/시간/내용) 확인.
- **회원탈퇴**: 애플 앱스토어 심사 필수 요건(계정 생성 기능 제공 시 앱 내 탈퇴 기능 필수).
- **즐겨찾기 미포함**: 로그인 없이 쓰는 기존 기능이므로 마이페이지에 넣지 않고 홈 상단 위치 유지.

## 8. 미해결 / 추후 과제

- 이력서 관리 사이트별 분리 여부 (추가 분석 필요, 사용자 보류)
- 지원완료 감지 로직 (사이트별 제출완료 URL/셀렉터, 로그인 필요해 미착수)
- 이용약관 / 개인정보처리방침 / 제3자제공동의서 법적 문서 텍스트 작성
- K-HIRE 로그인 성공 후 사이트 자체 홈으로 튕기는 문제 — WebView가 URL 감시하다 원래 공고 URL로 재이동시키는 방식으로 해결 예정(설계만, 미구현)
- 지원폼(온라인지원/간편입사지원) 필드 확인 — 로그인 후 HTML 필요, 미착수
- apply_contact 커버리지 조사 (문자/이메일 방식 공고 중 수신처 수집 비율)
- 지원문 템플릿 초안 (문자용/이메일용 한국어 대필 문구)
- 소셜 로그인 팝업(화면1) 취소 시 흐름 — 로그인 안 하고 WebView 계속 진행 허용할지, 로그인 필요한 방법 자체를 막을지 미정
- 페이스북 로그인 시 사용자가 이메일 제공을 거부할 수 있음 — 이 경우 화면2에서 이메일 입력받는 예외 처리 필요(구글/애플은 항상 제공하므로 무관)
- 회원탈퇴 시 서버 저장 개인정보(비자/국적/생년월일 등) 실제 파기 처리 — 개인정보보호법상 필요, 구현 미정
- 신규 DB 스키마 설계 전체 미착수 (계정/프로필, 지원이력, 문자·이메일 발송기록 저장할 Supabase 테이블)
