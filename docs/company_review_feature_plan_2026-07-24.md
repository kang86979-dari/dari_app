## 0. 핵심 전제 & Dari 고유 특수성

블라인드형 리뷰는 화면 하나 추가가 아니라 **신원 · 회사 엔티티 · 번역 · 법적 리스크**가 얽힌 기능군이다.
블라인드를 그대로 복제하면 안 되는 이유(Dari 특수성):

- **사용자 = 외국인 구직자** → 카카오/한국 전화 인증이 진입장벽일 수 있음. 다국어 필수.
- **고용주 = 소규모/비법인 사업장 다수** (공장·식당·농장·건설) → 블라인드의 **회사 이메일 재직검증 모델을 못 씀**. 사업자번호 등 확실한 키도 없을 수 있음.
- **8개 크롤링 소스** → 같은 회사가 표기·소스마다 다르게 들어옴. 회사 정규화 난이도 높음.
- **다국어 리뷰** → 벵골어로 쓴 리뷰를 베트남어 사용자가 봐야 함 → 자동 번역 필수 (기존 인프라 재활용 가능).
- **법적**: 한국 명예훼손법은 **사실 적시도 처벌 대상**(정보통신망법 제70조). 플랫폼 책임 → 신고/게시중단 프로세스 필수.

## A. 선행 인프라 (없으면 리뷰 성립 불가)

### A-1. 회사 엔티티 정규화 ⚠️ 최우선
- 현재 `jobs.company`는 **자유 텍스트 문자열**. 전용 companies 테이블 없음.
- 리뷰는 "회사"에 붙는데 같은 회사가 "(주)ABC" / "ABC" / "에이비씨"처럼 제각각.
- 필요:
  - `companies` 테이블 (id, 정규화명, 별칭 목록, 사업자번호(선택), 지역, 로고 등)
  - `jobs.company_id` FK + 기존 공고 매핑(백필)
  - 표기 정규화 + 중복 병합(dedup). pg_trgm 유사도 활용 가능(기존 검색에 이미 사용 중)
- 담당: 앱 Claude가 RPC/DB/스키마, 크롤러는 원문 company 텍스트 제공 (기존 분업 규칙)

### A-2. 사용자 인증/신원 ⚠️ 최우선 — ✅ 결정됨
- 현재 로그인 없음 (익명 session_id + SharedPreferences).
- 리뷰엔 작성자 신원 필요: 1인 1리뷰, 스팸 방지, 신고 대응, 본인 리뷰 수정/삭제.
- **결정: Supabase Auth 소셜 로그인 구글 / 페이스북 / 애플.** (애플 로그인은 iOS App Store 심사상 소셜 로그인 제공 시 필수이므로 iOS 대비 포함)
- 구현: `supabase_flutter` 이미 사용 중 → `signInWithOAuth`(google/facebook/apple). auth.users.id를 리뷰 작성자 FK로.
- 리뷰는 로그인하되 화면엔 익명(닉네임/국적) 표시.

### A-3. 신뢰·검증 모델 — ✅ 결정됨 (검증 안 함)
- **결정: 재직 검증 안 함.** 회사 이메일/증빙 요구 X.
- 대신 로그인 + **AI 후처리 모더레이션**(§F)으로 품질 관리. 스팸은 일부 감수.
- (추후 옵션) "Dari 통해 지원함" 뱃지로 점진 신뢰 강화 — MVP 제외.

### A-4. 모더레이션·법적 대응 ⚠️
- 신고 → 임시 게시중단(블라인드 처리) → 검토 프로세스.
- 이용약관 + 리뷰 가이드라인(다국어).
- 명예훼손·개인정보(실명 등) 노출 방지 필터.

## B. 핵심 리뷰 기능 (MVP)

- **종합 별점** (1~5)
- **세부 항목별 별점**:
  - 급여·복지 / 워라밸 / 근무환경(안전·기숙사) / 상사·관리 / **외국인 대우(차별 여부)** ← Dari 특화
- **장점 / 단점** 텍스트
- **작성자 메타**: 재직상태(재직/퇴사), 고용형태, 근무기간, 직무, 비자유형(선택)
- **1인 1회사 1리뷰**, 수정/삭제
- **익명 표시**: 닉네임/국적 정도만, 개인식별 불가

## C. 회사 프로필 화면

- 평균 별점 + 리뷰 수 + 별점 분포 그래프
- 세부 항목별 평균
- 리뷰 리스트 (정렬: 최신/평점/도움순, 필터: 언어/재직상태)
- **해당 회사의 현재 채용공고 연결** ← 기존 jobs 연동, Dari만의 강점
- (확장) 급여 통계, 면접 후기

## D. 다국어 처리 (Dari 최대 차별점) — 🔶 세부안 논의 중

리뷰는 감정·구어체·뉘앙스가 많아 공고 설명(정형 텍스트)보다 기계번역 품질이 떨어짐 + 언어쌍이 16×16으로 폭발. 접근안:

- **안 A) 온디맨드 기계번역** (기존 description과 동일): 원문 저장 + 뷰어 언어로 번역, jsonb 캐시. 장점=기존 인프라 재활용, 전부 읽힘. 단점=구어체 번역 품질·비용.
- **안 B) 피벗 번역**: 원문 → 영어(정본) → 각 언어. 언어쌍 축소. 단점=이중번역 품질 저하.
- **안 C) 원문 + "번역" 버튼(지연 번역)**: 요청 시에만 번역. 저렴·정직. 단점=낯선 문자 리뷰 탐색성↓.
- **안 D) 구조화 + 태그 중심** ⭐추천 기반: 별점 + **사전 번역된 고정 태그**(예: "야근 많음"/"급여 정시"/"기숙사 제공"/"외국인 차별 있음")를 주력으로, 자유서술은 짧게. 태그·별점은 16개 언어 1회 번역으로 **즉시 다국어**·번역비용 0·명예훼손 리스크↓. 자유서술만 온디맨드 번역.

### 유력안: D(구조화 태그) + Claude 번역·모더레이션 통합
- 자유서술 번역을 **Google Translate 대신 Claude로** 하면 구어체·뉘앙스 품질↑.
- **핵심 시너지**: §F의 AI 모더레이션 Edge Function 호출 **한 번**에 ①스팸/욕설/명예훼손 판정 + ②원문→영어(피벗) 번역을 **동시 처리**(structured output). 이후 영어→각 언어는 온디맨드.
- "원문 보기 / 번역 보기" 토글 (상세화면 주소 토글과 동일 UX).
- **결정 필요**: 자유서술 허용 범위(태그 위주 vs 자유서술 병행), 번역 주체(Claude vs Google), 피벗(영어) 채택 여부.

## E. 탐색·발견

- 회사 검색(평점 노출), 평점 높은/리뷰 많은 회사 랭킹
- 공고 카드/상세 → 회사 리뷰 진입 동선
- **정책**: 최소 리뷰 수 미만이면 평점 숨김 (리뷰 1~2개로 평판 왜곡 방지)

## F. 안전·신고·운영 — AI 모더레이션 (✅ 방향 결정)

### AI(Claude) 후처리 모더레이션
- **구조**: 리뷰 제출 → DB에 `status='pending'` 저장 → **Supabase Edge Function이 Claude API 호출**(기존 translate-description Edge Function과 동일 패턴, [[project_roles]] 앱 Claude 담당) → 판정 결과로 `status` 갱신(active/hidden/flagged).
- **분류 항목**: 스팸/광고, 욕설·혐오, 개인정보(실명·전화 등) 노출, 명예훼손 소지, 주제 무관, 언어 판별.
- **structured output**(`output_config.format` JSON 스키마)로 판정 결과를 정형 수신 → 파싱 안정.
- **모델**: 기본 `claude-opus-4-8`. 대량·저비용 분류라 `claude-haiku-4-5`($1/$5 per 1M)도 적합 — 비용/품질 보고 결정(모델 강등은 사용자 결정 사항). 실시간 아니어도 되면 **Batch API(50% 저렴)** 활용 가능.
- **번역 통합**: §D처럼 모더레이션 호출에 원문→영어 피벗 번역을 함께 시켜 1콜 처리 검토.
- **비동기 처리**: 제출 즉시 pending 노출/보류 정책 결정 필요(제출자에겐 바로 보이되 타인에겐 판정 후 노출 등).

### 그 외
- 사용자 신고(허위/욕설/개인정보/명예훼손) → 임시 블라인드 (AI 자동 + 사용자 신고 병행)
- rate limit(1인 1회사 1리뷰 + 작성 빈도 제한), 중복/스팸 탐지
- **관리자 모더레이션 도구**(웹/관리 화면 — 별도 작업, MVP 후순위): AI가 flagged 처리한 건 사람이 최종 확인
- 이용약관·리뷰 가이드라인(다국어) — 명예훼손 법적 방어선

## DB 스키마 스케치 (초안, 확정 아님)

```
companies
  ├── id (uuid, PK)
  ├── name_normalized (text)         정규화 대표명
  ├── aliases (text[])               크롤링 표기 변형들
  ├── biz_reg_no (text, nullable)    사업자번호(있으면)
  ├── region_id (FK → regions, nullable)
  ├── review_count (int)             비정규화 캐시
  ├── rating_avg (numeric)           비정규화 캐시
  └── created_at

jobs
  └── company_id (FK → companies)    ★ 신규 컬럼 + 백필

company_reviews
  ├── id (uuid, PK)
  ├── company_id (FK → companies)
  ├── user_id (FK → auth.users)
  ├── rating_overall (int 1~5)
  ├── rating_salary / rating_worklife / rating_env
  │   / rating_management / rating_foreigner (int 1~5)
  ├── pros (text), cons (text)
  ├── employment_status (text: current/former)
  ├── employment_type, job_title, work_period, visa_type (nullable)
  ├── lang_code (text)               원문 언어
  ├── pros_translations / cons_translations (jsonb)  온디맨드 캐시
  ├── status (text: active/hidden/pending)
  ├── helpful_count (int)
  ├── created_at, updated_at
  └── UNIQUE(company_id, user_id)    1인 1회사 1리뷰

review_reports
  ├── id, review_id (FK), reporter_user_id
  ├── reason (text), detail (text)
  └── created_at

review_helpful               (도움돼요)
  ├── review_id (FK), user_id (FK)
  └── UNIQUE(review_id, user_id)
```

RPC(예정): get_company_profile, get_company_reviews(정렬/필터/페이지), submit_review, report_review, toggle_helpful, translate_review

## 남은 결정 (다국어 세부안)

인증·검증·모더레이션 방향은 확정(상단 결정사항 표). 남은 건 §D 다국어 세부:

1. **자유서술 범위** — 태그 위주(최소 자유서술) vs 자유서술 병행?
2. **번역 주체** — Claude(품질↑, 모더레이션과 1콜 통합) vs Google Translate(기존 인프라)?
3. **피벗 언어(영어) 채택** — 원문→영어→각 언어 방식 쓸지?

→ 다국어 세부안 확정 시 **DB 스키마 확정 + 화면 흐름 + 단계별 구현 계획**으로 진행.
MVP 범위(잠정): A-1 회사정규화 + A-2 소셜인증 + B 핵심리뷰 + C 회사프로필기본 + D 다국어 + F AI모더레이션. 커뮤니티·급여통계·관리자툴·증빙검증은 2차.

## 리스크 요약

- 🔴 **명예훼손 법적 리스크** (한국은 사실도 처벌) → 약관·신고·게시중단 필수, 초기 보수적 운영
- 🔴 **회사 정규화** 실패 시 리뷰가 엉뚱한 회사에 붙음 → 데이터 신뢰 붕괴
- 🟡 **콜드스타트**: 리뷰 없는 회사가 대부분 → 초기 확보 전략 필요(예: 지원 후 리뷰 유도)
- 🟡 **인증 진입장벽** vs 스팸 방지 트레이드오프
