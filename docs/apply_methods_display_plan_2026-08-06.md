# 상세화면 "지원방법 표시" 기능 — 방향 구상 (2026-08-06)

관련: `docs/apply_autofill_plan_2026-07-28.md`, 메모 `project_apply_scenario`.
성격: 큰 지원-가이드 시나리오의 **앞단계(표시 전용)**. 착수 전, 방향 정리 단계.

## 목표
공고 상세화면에서 그 공고의 **지원방법 종류**(온라인/문자/전화/이메일/간편/홈페이지/채팅/방문 등)를 사용자에게 보여준다.

## 핵심 난점 — 데이터 출처
- 지원방법은 각 사이트에서 **JS로 렌더되는 지원 레이어 안**에 있음 (예: K-HIRE `.applyLayer__link--{tel|online|sms|simple|market|homepage}`).
- **크롤러는 현재 목록/기본정보(제목·급여·지역 등)만 수집** — 지원방법은 안 가져옴.
- 그래서 기존 시나리오는 "크롤 때 수집"이 아니라 **[지원하기] 누를 때 그 공고 페이지를 실시간 파싱**하기로 했었음.
- ⚠️ raw HTML엔 실제 렌더보다 방법이 많이 들어있음(예: 공고 145899500 raw=homepage/market/simple/tel, 실제노출=tel/market) → 파싱 시 실제 노출 방법만 거르는 로직 필요.

## 데이터 출처 3안

### 1안. 크롤러가 공고 상세를 헤드리스 렌더 → 방법 추출 → DB 저장
- 장점: 공고별 정확, 앱은 읽어서 표시만(빠름, 오프라인 무관)
- 단점: 크롤러가 **공고 하나하나 브라우저 렌더**(수만 건 × 사이트별 파싱) → 부하 큼
- 전제: 크롤러가 JS 렌더를 하는지 여부 (미확인 → 사용자 확인 필요)

### 2안. 상세화면 열 때 그 공고 1건만 실시간 파싱 (앱 or Edge Function)
- 장점: 크롤러 안 건드림
- 단점: 상세 열 때마다 지연, 사이트별 파싱 규칙을 서버가 보유해야 함

### 3안. 사이트 단위 기본 지원방법 맵 (공고별 아님)
- 예: "K-HIRE = 온라인/문자/전화/간편" 식 사이트별 고정 표시
- 장점: 크롤 불필요·즉시·단순
- 단점: 부정확(공고마다 실제 방법 다른데 뭉뚱그림)

## 정규화 코드(taxonomy) — 사이트 용어 → 공통 코드
`online`(온라인) / `homepage`(홈페이지) / `email`(이메일) / `phone`(전화·전화후방문) /
`sms`(문자) / `simple`(간편) / `chat`(채팅) / `visit`(방문)
- 사이트별 원문 → 위 코드 매핑, **매핑표는 서버/크롤러 관리**(앱 업데이트 없이 확장).

## 앱 측 설계(출처 확정 후 공통)
- DB: `jobs.apply_methods text[]`(또는 jsonb 배열, 코드값) 신규 컬럼, RPC 반환 포함
- 모델: `Job.applyMethods: List<String>` + `getApplyMethodLabel(code, lang)`
- 다국어: `app_strings`에 코드별 라벨 16개 언어 (크롤 한국어 안 씀)
- **UI 위치 확정(2026-08-07)**: **핵심정보 테이블에 "지원방법" 행** 추가 (급여/근무시간 등과 동일 형식). B/C안 아님.
- **표현 확정**: **아이콘 + 라벨 칩** (예: `[🖥 온라인 지원] [💬 문자] [📞 전화]`).
- 레이아웃: 값 영역에 칩 **Wrap**(방법 많으면 자동 줄바꿈, 행 높이 확장). 기존 `_InfoRow`(텍스트 전용)와 별개로 **칩 Wrap용 변형 행**(`_InfoChipsRow` 등) 필요.
- 아이콘 매핑(예): online🖥 homepage🌐 email✉ phone📞 sms💬 simple⚡ chat💬 visit📍 (실제 Material 아이콘으로 구현)
- 예외: 데이터 없음/ testing 사이트 → **행 숨김**(기존 빈행 숨김 규칙과 동일)

## 동작 범위 단계
- **1단계(이 기능): 표시 전용** — 방법 칩만, [지원하러 가기]는 기존 흐름(웹뷰/사파리) 유지, 칩 탭 동작 없음
- **2단계(추후): 칩 탭 → 방법별 분기**(phone→전화, email→메일, 그 외→웹뷰) — project_apply_scenario와 연결

## 결론(현재)
데이터 출처가 미해결이라 앱 UI보다 **"지원방법을 어디서 어떻게 확보하느냐"가 먼저**.
크롤러가 상세를 JS 렌더하는지 확인 → 1안 가능하면 정확/저지연, 불가하면 2안(실시간 파싱) 또는 3안(사이트 단위 대략)으로.
